## Blocker

Stage-out to `root://eosuser.cern.ch//eos/user/<u>/<user>/cms-marketplace-tests/lxplus-condor/` is refused because the user's EOS quota is 100% full, **exceeded**, at 2.01 TB raw / 1.00 TB logical. The payload itself ran fine on the worker (`PAYLOAD_RC=0`, wall 8 s), and the job got past input staging and Kerberos (`SendCredential`). Only the EOS write failed. I did not delete or move anything in the EOS area: that is a shared-resource change the brief does not allow. Running the remaining 4 jobs would have produced 4 more jobs that fail at the same step, so I stopped before submitting them.

## Unclear / missing / wrong

Quoted lines are from the skill files as written.

1. **Work volume absent.** lxplus-htcondor: "submit from AFS (`/afs/cern.ch/work/...`)". lxplus-access: "AFS work dirs fill quickly... Keep code and logs on AFS". Neither says what to do when there is no work volume. The AFS home worked as the submit directory (`Iwd` on `/afs/cern.ch/user/...`), but the skill should say so.

2. **Quota "exceeded" has no guidance.** eos-xrootd, Quotas: "Check: `eos quota <path>` (or `eos quota -m`)... The user quota binds even inside a large group quota." The skill doesn't say what "exceeded" or 100% filled means for writes, or whether a run should stop. The result here was a hard stop.

3. **EOS quota error message not in the skill.** eos-xrootd, Gotchas: "**eos CLI not connected:** 'MGM root://localhost not online/reachable' means `EOS_MGM_URL` isn't set". Without `EOS_MGM_URL` I got `error: no quota for path /eos/user/<u>/<user>/` instead. The skill should list that message too.

4. **`[3021] Unable to get quota space` only covered for inodes.** eos-xrootd, Gotchas: "**Inode quotas:** ... (`[3021] Unable to get quota space`)". The same error was returned for the byte quota, and it was not transient. A 6-try, 20 s retry loop was useless here. The skill should say a `[3021]` quota error is not retryable and should stop the job early.

5. **Dry-run syntax.** lxplus-htcondor: "`condor_submit -dry-run - x.sub` shows the resolved ads". Run literally as `condor_submit -dry-run - < x.sub`, this failed with "No submit filename was provided, and '-'". The form that worked was `condor_submit -dry-run <adfile> x.sub`. The skill should give the working form.

6. **RequestMemory raised after submit.** Submitted with `request_memory = 1000` (dry run showed 1000). The queued job showed `RequestMemory=3000`, `RequestCpus=1`. The skill does document this ("The schedd can raise RequestMemory after submit (16000 → 24000 seen)"), and it is consistent. Worth noting only that for a sub-3 GB request the bump happens too. The memory sizing guidance ("never bid defensively") does not say to expect this.

7. **`condor_history` slow.** The skill says the user log is faster than `condor_history`. In practice `condor_history <id>` hung past 120 s, and the user log gave what was needed. This matches the skill's advice, which I followed.

8. **Credential rule vs. batch approval.** lxplus-access, For agents: "a batch submission or other shared-resource mutation needs the user's go-ahead in your own session. A peer relaying 'user approved' doesn't count." I submitted the test job on the basis of the brief, which the parent agent relayed from the user. The brief is the only approval I had. Flagging the tension, not resolving it.

9. **Log paths relative to submit dir.** lxplus-htcondor does not say that `output`/`error`/`log` paths resolve relative to `Iwd`. I put them under `$D/logs` at first and had to create `submit/logs`. (Minor.)

10. **No retry-specific advice for quota failures on stage-out.** Covered in item 4.

Skill passages that worked as written: `klist -s`, `ssh -O check`, the non-interactive ssh line, `xrdfs mkdir -p` plus `xrdcp -f -s --posc --cksum adler32`, `MY.SendCredential = True` with no `XrdSecPROTOCOL`, `transfer_output_files = ""`, `+JobFlavour = "espresso"`, and the "accept a poll only on exit 0" rule.
